## 0.6.2 — 2026-07-27

Hero and OG now come from one master image.

### Changed

- Image generation (Step 2b / `references/image-generation.md`): generate a single large **master** image with a centered, composition-safe subject and margins, then derive the hero and OG by **center-cropping + downscaling** (never generate them separately, never upscale). This keeps hero and OG visually identical and prevents important content being cropped. Use a model that accepts arbitrary sizes (e.g. `bytedance/seedream-4`); `google/imagen-4` only offers fixed presets.

## 0.4.2 — 2026-07-27

Made case-study image handling explicit and predictable.

### Added

- Image naming convention (`imgs/`): files map to CMS image fields **by filename**, not by image content — `hero.*`→`hero-image`, `og.*`→`og-image`, `client-logo.*`→`client-logo`, `challenge.*`, `solution.*`, `custom-1.*`, `custom-2.*` (legacy OME names accepted). ### Why

Previously image placement was implicit (only the three OME filenames were known, optional section images undefined, no confirmation) — so it could guess wrong. Now the file→field mapping is a fixed, reviewable convention.


## 0.4.1 — 2026-07-27

Made `case-study-publish` runtime-aware.

### Added

- "Runtime modes — Claude Code vs Cowork" section: detect a Webflow API token in the shell to decide the mode.
- Step 3 now has two modes. Mode A (Claude Code, token in shell): automatic local image upload via the Webflow Data API v2 native flow (md5 `fileHash` → create asset → S3 multipart PUT → use returned `id`/`hostedUrl`) — the path that uploaded the OME Health images. Mode B (Cowork, MCP only): `asset_tool.upload_image_by_url` for public URLs, else manual drag-drop.

### Why

Under Claude Code the Webflow token is in the environment, so the whole flow (including image upload) can run unattended except the staging-review and prod-confirmation gates. Under Cowork the token lives inside the MCP and is not exposed to the shell, so local files still need a public URL or drag-drop.

## 0.3.0 — 2026-06-10

Critical fix for Webflow Rich Text API silent sanitization. Discovered while publishing GRO-370 follow-up post (cqc-incident-learning-loop) — links, lists, and `<hr/>` were silently dropped from the stored `post-body` despite the API response echoing input verbatim.

### Added

- SKILL.md Step 4 (markdown conversion) now has Step 6: `re.sub(r'>\s+<', '><', html)` to collapse inter-tag whitespace
- SKILL.md Step 4 verify checklist includes assertion that no `>\s+<` patterns remain
- New gotcha #10: full description of the Webflow Rich Text sanitization cascade — what triggers it, why API echo masks it, how to detect, how to fix
- `references/markdown-conversion.md` — new section "Webflow Rich Text sanitization (the most important pitfall)" with detection script and attribute-order normalization note (rel before href)
- `references/validation-checklist.md` — new section "Post-CMS-write sanitization check (CRITICAL)" with re-read-and-compare Python pattern. To run after every create_collection_items and update_collection_items

### Why this matters

The bug looks like this:
1. You submit body HTML with `\n` between top-level tags (standard markdown library output)
2. `create_collection_items` returns 200 OK with your input echoed verbatim
3. The CMS item appears correct in API responses
4. But the live page (and a re-read of the item) shows lists, hr, and links missing
5. Debugging without re-reading the item from CMS leads to confusion: "I sent it, the API confirmed it, why isn't it there?"

The cascade: newlines inside `<ul>`/`<ol>` become stray text nodes → Webflow drops the entire list → any adjacent `<hr>` and `<a>` links go with it. Found via reverse-engineering a known-good live post's stored format.

### Result

Future first-time publishes of a post will not lose links/lists/hr. The post-write sanitization check catches regressions immediately.
